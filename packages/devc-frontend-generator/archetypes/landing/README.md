## 마케팅 랜딩

랜딩 Archetype으로 만들었습니다. `i18n`(locale이 붙은 주소와 언어 전환), `seo`(메타데이터, 공유 이미지, sitemap) Recipe를 조합한 마케팅 랜딩 페이지가 `/ko/landing`, `/en/landing`에 있습니다. 머리글의 "랜딩"(영어 페이지에서는 "Landing") 링크로 들어갑니다.

| 위치                                              | 내용                                                                                                                                                 |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/app/[locale]/landing/page.tsx`               | 랜딩 페이지. locale마다 빌드할 때 미리 렌더링하고(SSG), 콘텐츠의 제목·설명과 locale별 주소, 공유 이미지를 메타데이터로 알림                          |
| `src/app/[locale]/landing/og-image.png/route.tsx` | locale별 공유 이미지(`/ko/landing/og-image.png`, `/en/landing/og-image.png`). `seo` Recipe의 `ogImage`로 그림                                        |
| `src/features/landing/`                           | 화면(`landing.tsx`: 히어로, 주요 기능, 고객 후기, 자주 묻는 질문), 서버에서 콘텐츠 가져오기(`landing-content.ts`), 머리글의 링크(`landing-link.tsx`) |
| `src/queries/landing/`                            | `npm run g -- query getLandingPage`가 만든 코드 그대로                                                                                               |
| `src/shared/mocks/landing.ts`                     | locale마다 다른 콘텐츠를 돌려주는 목 백엔드                                                                                                          |

- 콘텐츠: 페이지의 문구는 헤드리스 CMS처럼 백엔드가 locale마다 돌려줍니다. 명세(`openapi.yaml`)의 `landing` tag에 있는 `getLandingPage`(`GET /landing-pages/{locale}`)가 검색 결과와 공유 카드에 보일 제목·설명, 히어로, 주요 기능, 고객 후기, 자주 묻는 질문을 한 번에 돌려주고, 그 locale로 쓴 콘텐츠가 없으면 404입니다. 스키마는 `LandingPageContent`처럼 `Landing`으로 시작합니다. 섹션을 더하려면 명세에 스키마를 더하고 `npm run api:gen`을 실행한 뒤 `src/features/landing/landing.tsx`에 섹션을 더합니다. 히어로의 링크(`#features`)처럼 콘텐츠가 가리키는 섹션의 id는 `features`, `testimonials`, `faqs`입니다.
- 렌더링(SSG): 페이지는 i18n Recipe의 `[locale]` 레이아웃이 정한 locale마다 빌드할 때 콘텐츠를 가져와 미리 렌더링합니다. `dynamic = 'error'`라 요청마다 달라지는 값(쿠키, 헤더 등)을 읽게 바뀌면 SSR로 바뀌는 대신 빌드가 실패합니다. 콘텐츠는 서버 컴포넌트가 props로 그리고 hydration으로 넘기지 않습니다(`src/features/landing/landing-content.ts`). 브라우저의 쿼리 캐시에 넘기면 `staleTime`이 지난 콘텐츠(빌드한 지 오래된 페이지는 처음부터 그렇습니다)를 브라우저가 다시 가져와, 배포한 정적 페이지가 방문마다 백엔드를 부르기 때문입니다. 그래서 콘텐츠를 바꾸면 다시 빌드합니다. 다시 빌드하지 않고 바꾼 콘텐츠를 반영하려면(server Starter만) `dynamic = 'error'` 대신 `export const revalidate = <초>`로 ISR을 씁니다.
- 빌드: 빌드할 때 콘텐츠 API를 부르므로 배포용 빌드에는 백엔드 주소 `API_BASE_URL`(과 `seo` Recipe의 `NEXT_PUBLIC_SITE_URL`)을 넣습니다. 없으면 빌드가 실패합니다. GitLab CI의 `build` 잡과 E2E는 목 빌드(`API_MOCKING=enabled`)로 목 백엔드의 콘텐츠를 담아 빌드하므로 그 결과는 배포하지 않습니다("배포용 빌드와 목 빌드"). static-export Starter에서는 `out/ko/landing.html`, `out/ko/landing/og-image.png`처럼 정적 파일이 되어, 백엔드 없이 정적 파일 서버에 올립니다.
- 언어: 문구는 콘텐츠 API가 locale마다 돌려주므로 메시지 카탈로그에는 머리글의 링크(`LandingLink`)만 더했습니다(`src/shared/i18n/ko.json`, `en.json`). 머리글의 언어 전환 UI로 다른 언어를 고르면 같은 랜딩 페이지의 그 언어 주소로 갑니다. locale을 더하려면 i18n Recipe의 방법("다국어(i18n)")으로 locale을 더하고 백엔드에 그 locale의 콘텐츠를 더합니다(목 백엔드는 `MOCK_LANDING_PAGES`).
- 검색 노출: 페이지는 콘텐츠의 제목·설명을 title·description(og:title·og:description, Twitter 카드)으로, 자기 주소를 canonical로, 같은 페이지의 locale별 주소와 x-default(기본 locale의 주소)를 hreflang으로 알립니다(`localeAlternates('/landing')`). og:locale은 `[locale]` 레이아웃이 알리고, sitemap에는 i18n Recipe의 sitemap 규칙이 locale마다 서로를 언어별 주소로 묶어 넣으므로 따로 적지 않습니다.
- 공유 이미지: locale마다 그 locale의 제목과 설명으로 그린 이미지(`og-image.png`)를 빌드할 때 만들고, 페이지의 metadata가 og:image(와 Twitter 카드의 이미지)로 알립니다. `seo` Recipe처럼 페이지 폴더에 `opengraph-image.tsx`를 두지 않는 것은, Next.js가 그 이미지 라우트에는 `[locale]` 레이아웃의 `generateStaticParams`를 쓰지 않아 locale마다 미리 만들지 못하기 때문입니다(static-export는 빌드가 실패합니다). 그래서 locale을 스스로 정하는 Route Handler(`generateStaticParams`)로 두고, 주소가 `.png`로 끝나 정적 파일 서버도 `image/png`로 응답합니다. `[locale]` 아래의 다른 번역 페이지에 공유 이미지를 따로 줄 때도 이 방법을 씁니다.
- 랜딩을 홈(`/ko`, `/en`)으로 쓰려면 `src/app/[locale]/landing/`의 페이지와 `og-image.png`를 `src/app/[locale]/`로 옮겨 i18n Recipe의 홈을 대신하고, 주소(`'/landing'`, `/${locale}/landing/og-image.png`)와 머리글의 링크를 고칩니다. static-export Starter의 `/`는 `src/app/page.tsx`가 그리므로 그 파일도 고칩니다.
- 목 백엔드: `src/shared/mocks/landing.ts`가 `ko`, `en` 콘텐츠를 돌려주고 그 밖의 locale은 404로 답합니다. 확장 지점 `mockHandlers`로 생성된 핸들러(늘 명세의 `example`인 `ko` 콘텐츠)보다 앞에 두고, 목 백엔드 주소(`MOCK_API_BASE_URL`)로 가는 요청만 받습니다. 실제 백엔드(CMS)로 바꾸면 이 파일과 그 테스트(`landing.test.ts`), `src/shared/mocks/handlers.ts`의 `landingHandlers`를 지웁니다. 스토리, 단위 테스트, E2E도 이 파일의 콘텐츠를 쓰므로 그때 함께 고칩니다.
- 테스트: `src/shared/mocks/landing.test.ts`(locale마다 다른 콘텐츠, 없는 locale은 404), `src/features/landing/landing.test.tsx`(섹션마다 제목으로 이름 붙은 랜드마크, 자주 묻는 질문 펼치기), `landing.stories.tsx`(ko·en, 펼친 답의 접근성), `e2e/landing.spec.ts`(주요 섹션, 브라우저가 콘텐츠를 다시 부르지 않음, 빌드할 때 렌더링한 HTML, 언어 전환, 머리글의 링크, 언어별 메타데이터와 공유 이미지, sitemap, 없는 locale의 404, 자주 묻는 질문을 펼친 상태까지 접근성).
- 랜딩을 지우려면 `src/app/[locale]/landing/`, `src/features/landing/`, `src/queries/landing/`, `src/shared/mocks/landing.ts`와 `landing.test.ts`(와 `handlers.ts`의 `landingHandlers`), `e2e/landing.spec.ts`를 지우고, `src/app/app-shell.tsx`의 `LandingLink`, 메시지 카탈로그의 `LandingLink`, `openapi.yaml`의 `landing` tag·경로·스키마를 뺀 뒤 `npm run api:gen`을 실행합니다.
